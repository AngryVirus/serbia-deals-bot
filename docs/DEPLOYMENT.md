# Подключение @SerbiaDealsBot

Проект предназначен только для нового бота. Не используйте ключ от @SerbiaJobsBot.
Перед любыми изменениями управление проверяет username через SDK `getMe`.

## 1. Репозиторий и проверки

Публичный репозиторий: `AngryVirus/serbia-deals-bot`.
После загрузки кода дождитесь успешных jobs `tests` и `security` в `Test deals bot`.
Actions закреплены по полным SHA. Проверки выполняют тесты, detect-secrets и npm audit;
у сборщика нет сторонних Python-зависимостей.

Если подключению отказано в настройке защиты main, владелец открывает
Settings → Branches → Add branch protection rule, шаблон `main`:

- Require a pull request before merging; обязательные одобрения можно не включать
  для репозитория с одним владельцем.
- Require status checks: `tests`, `security`; Require branches to be up to date.
- Запрет force push и удаления main; применить правила к администраторам.

Включайте правило после появления реальных успешных checks, а не до первой загрузки.

## 2. Отдельный ключ Telegram Serverless

Подключите **@SerbiaDealsBot** к Telegram Serverless через его собственные настройки.
Путь получения ключа проверен в исходном коде установленного официального CLI:
**@BotFather → ваш бот → Serverless → CLI Access → Access token**.
Официальный CLI `@tgcloud/cli` использует ключ формата `app<id>:…`.
Обычный HTTP Bot API token от BotFather не подходит для этого интерфейса.
Документация SDK:
https://core.telegram.org/bots/serverless

В GitHub: Settings → Secrets and variables → Actions → New repository secret:

`SERBIA_DEALS_CLOUD_TOKEN`

Значение вставляется только в защищённое поле GitHub. Не отправляйте его в чат,
issue, README, shell-команду или лог. Никакие секреты старого проекта менять не нужно.

## 3. Публикация кода без активации

Actions → **Serbia Deals maintenance** → Run workflow:

1. `action=stage`. Для первой установки `expected_revision` оставьте пустым.
   Команда проверит identity, создаст отдельные таблицы и загрузит код.
   Флаг active по умолчанию false; webhook на этом шаге не переключается.
2. `action=collect`, `sources=lidl,maxi,okov`. Это настоящий импорт публичных цен.
   Пока бот на паузе, сообщения пользователям не отправляются.
3. `action=check`. Проверьте состояние источников и отсутствие ошибок.
4. Прежде чем добавлять все источники, проверьте фактические размер SQLite,
   доступную квоту Telegram Serverless, длительность импорта и ограничения
   управляющего API. Локальная SQLite не подтверждает серверные квоты.
5. После этого `action=collect`, `sources=all` с контролем завершения. Бюджет одного
   прохода — 35 минут; незавершённые порции сохраняются и возобновляются.

Для последующего обновления кода нужен явно проверенный `expected_revision`.
Чужой или неожиданно изменившийся remote-код не перезаписывается автоматически.
После `stage` повторно считываются установленная ревизия и все исходники модулей:
успех подтверждается только при полном совпадении с загружаемым набором.

Перед публикацией `action=diagnose`, `require_deployed=false` проверяет локально
подготовленный код в среде Serverless без его установки. После публикации
`action=diagnose`, `require_deployed=true` также требует полного совпадения
проверяемого кода с установленным. Ошибка любой обязательной группы завершает
задание ошибкой; вывод содержит безопасные имена групп, не исходники. Преднамеренная
пауза допускается, очередь входящих обновлений сама по себе ошибкой не считается.

## 4. Активация — отдельное разрешение

До разрешения владельца `activate` не запускается. После разрешения:

1. `action=activate`. Требуется минимум один опубликованный реальный прайс.
2. Проверить `/start`, поиск «лампочка E27», карточку, ввод списка и сравнение корзины
   в Telegram владельцем. Проверить PNG и редактирование картинок.
3. Пройти проверку уведомления на специально согласованном тестовом пользователе.
   Не включать реальные пользовательские рассылки ради теста.
4. Проверить экспорт/восстановление нужных данных перед публичным релизом.

## 5. Плановые задания

По умолчанию расписания работают с ограниченным списком уже проверенных источников
из `collector/enabled-sources.json`: Lidl, Maxi, Okov, Gomex, Matijević, Lilly, METRO и Aman.
Проверка прайсов всех 47 кандидатов и их массовый импорт автоматически не запускаются.
Новые сети включаются в этот список после проверки свежего CSV и контролируемого импорта.

Подготовительный шаг строит матрицу из этого же списка; каждый магазин получает
отдельное последовательное задание с 40-минутным бюджетом импорта. Отказ магазина
не отменяет остальные задания. Частичный успех не выдаётся за полный: Actions
показывает неуспешные сети, а обработка уведомлений запускается и после частичного
обновления. Проверка здоровья после каждой сети сообщает только новые сбои или
восстановление. Независимый watchdog сохранён.

Очистка удаляет только устаревшие технические поколения, SQL-порциями до 250
предложений, максимум четыре порции за запрос. После публикации выполняется до
четырёх запросов очистки, остальное продолжается позже. Действующий прайс,
подготавливаемое поколение, корзины и подписки очистка не затрагивает. Двухдневный
порог свежести не продлевается. Для ручного восстановления одной сети выберите
`action=collect` и её alias в `sources`, например `lilly` или `okov`.

Файловое хранилище Aman/Matijević отвечает HTTP 400 на неподдерживаемый путь
`/robots.txt`. Как и 404/410, такой ответ означает отсутствие файла правил
([RFC 9309 §2.3.1.3](https://www.rfc-editor.org/rfc/rfc9309.html#section-2.3.1.3)).
Действующие правила robots.txt соблюдаются; 401/403, 429, сетевые и серверные
ошибки его загрузки останавливают попытку. Доступ к самому CSV, разрешённые
публичные хосты, лицензия и даты проверяются отдельно; ответ об ошибке CSV
никогда не превращается в успешную загрузку.

Repository variables сохраняют возможность явного отключения:

- `SERBIA_DEALS_COLLECTION_ENABLED=false` — отключить плановый сбор и обработку
  пользовательских уведомлений; `true` или отсутствие значения разрешает их.
- `SERBIA_DEALS_MONITOR_ENABLED=false` — отключить независимую проверку раз
  в 12 часов; `true` или отсутствие значения разрешает её.

Уведомления о снижении цены отправляются после успешного планового сбора и
дополнительно каждые 6 часов, только пользователям, включившим подписку.
Ручная команда `collect` в maintenance обновляет прайсы без тестовой рассылки.

Плановый и ручной `collect`, а также тяжёлые `stage`, `diagnose`, `check` и
`quality` используют одну группу выполнения `serbia-deals-collect`: импорт
цен не пересекается с другим импортом или массовой служебной диагностикой,
чтобы они не отнимали друг у друга квоту управления Telegram Cloud.
Проверка здоровья, ценовые уведомления и доставка уведомлений доступа/рекламы
используют отдельные группы. Поэтому долгий импорт не вытесняет их ожидающие
запуски. Остальные ручные операции maintenance имеют собственную группу.
Согласованность поколений, пользовательских действий и отправок обеспечивают
также атомарные запросы и аренды в SQLite. Уведомления доступа и рекламная
очередь проверяются существующим заданием раз в 15 минут.

Сбор назначен каждые шесть часов, на 00:21, 06:21, 12:21 и 18:21 UTC.
Это позволяет повторить попытку после временного отказа или позднего обновления
файла в течение дня. Неизменившийся файл не импортируется заново; его исходная
дата не продлевается фактом скачивания.
GitHub schedule может задерживаться. В интерфейсе нет обещания обновлений каждую минуту.
Предупреждения владельцу — при отсутствии успешного прохода более 36 часов,
устаревшем прайсе любой используемой сети либо росте проблем доставки.
Успех одной сети не скрывает проблему другой. Восстановление каждого направления
отслеживается отдельно; одинаковые состояния подавляются атомарно.
Ручные импорты отдельных источников не заменяют ожидаемый список планового сбора.

Используются стандартные Ubuntu runners. Для public-репозитория это бесплатная
инфраструктура; платные runners и сервисы не подключаются. Квоты самой платформы
Serverless до реального подключения не подтверждены.

`pause` выключает ответы и отправку уведомлений, не удаляя каталог и корзины.
Сбор можно остановить установкой переменной в `false` и отменой соответствующего Actions run.

## Гарантии и ограничения

- Публикация каталога по каждому источнику атомарна: старое поколение остаётся
  доступным до полного окончания загрузки нового.
- Пакеты и callbacks идемпотентны; обработка одного пользователя сериализована.
- Каждая корзина читает предложения одним SQLite-запросом, не смешивая поколения.
- Состояние отправки фиксируется **до** обращения к Telegram. Неопределённый
  результат не отправляется повторно автоматически. Это предотвращает дубли,
  но не является гарантией exactly-once; при сбое возможно пропущенное сообщение.
- Явный 429 оставляет доставку в очереди с retry_after. 403 отключает отправки
  заблокировавшему бота пользователю.
- Служебные результаты отправки удаляются через 10 дней. Пользователь может
  удалить корзину, подписки, настройки, очередь и записи своих обновлений.
